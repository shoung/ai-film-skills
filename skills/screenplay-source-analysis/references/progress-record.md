
# 章級進度、驗證與 QA 狀態紀錄手冊 (progress-record)

本手冊規範分析任務之進度管理、斷點續跑作業、結構驗證與獨立 QA 狀態管制標準。

## 1. 章級進度追蹤標準

逐章分析時必須維持結構化追蹤紀錄，以便於多人協作、進度稽核與中斷續跑。

### 1.1 命名規範
- 分析檔案必須統一命名為：`ch-<sequence>-extract.md`。
- `sequence` 建議採用 4 位數補零格式（如 `ch-0001-extract.md`）或固定整數格式（如 `ch-1-extract.md`），全專案必須保持風格一致。

### 1.2 進度追蹤表格式範本
```markdown
# 原著章級分析進度表

- 原著檔案：`輸入/novel.txt`
- 索引檔案：`cache/novel_index.json`
- 本批來源 SHA-256：`<與索引 source.sha256 一致的 64 位小寫十六進位雜湊>`
- 驗證狀態：已通過 verify 比對
- 目標範圍：第 1 章 至 第 50 章

| 章序 (Seq) | 原文章節標題 | 起訖行 (line_start ~ line_end) | 分析檔名 | 分析狀態 | 警示標記 | 備註 |
| :---: | :--- | :---: | :--- | :---: | :---: | :--- |
| 1 | 第一章 少年出谷 | 1 ~ 120 | ch-0001-extract.md | 完成 | - | 建立核心主角背景 |
| 2 | 第二章 意外遇險 | 121 ~ 245 | ch-0002-extract.md | 完成 | - | 引入反派危機 |
| 3 | 第三章 退婚風波 | 246 ~ 380 | ch-0003-extract.md | 完成 | - | 第一幕衝突點 |
| 4 | 第五章 宗門秘藏 | 381 ~ 490 | ch-0004-extract.md | 完成 | 跳章 (Gap) | 原文缺第 4 章標題，已註記 |
| 5 | 第五章 重入深淵 | 491 ~ 510 | ch-0005-extract.md | 完成 | 重章 (Dup), 短章 (Short) | 章名重複且行數過短 |
| 6 | 第六章 絕處逢生 | 511 ~ 650 | ch-0006-extract.md | 進行中 | - | - |
```

每份逐章分析檔第一行均須包含來源版本標記：

```markdown
<!-- source_sha256: <索引 source.sha256 的 64 位小寫十六進位值> -->
```

正式檢查一律使用 strict 模式：

```bash
python scripts/novel_index.py coverage cache/novel_index.json analysis_output/ --require-source-hash --start 1 --end 50
```

`unverified_files` 表示缺少或無法讀取來源標記；`stale_files` 表示標記與本批索引來源雜湊不同。兩者非空都會使 `complete` 為 false。此標記只綁定來源版本，不是重新分析的證明；不可手動更改舊檔標記。

## 2. 斷點續跑與增量拆解操作手冊

若分析過程因故中斷，或採分批次提取（例如先分析前 20 章，後續再分析 21–50 章），應依下列流程復原並續跑。來源原文或索引雜湊改變後，保留舊章分析及舊 QA 作為舊版本紀錄，另開新批次重新分析並重新 QA；不得只改舊標記、刪除舊資料或沿用舊 QA 冒稱完成。

### 2.1 檢查既有進度
執行 `coverage` 盤點現有檔案並偵測缺漏：
```bash
python scripts/novel_index.py coverage cache/novel_index.json analysis_output/ --require-source-hash --start 1 --end 50
```
- 此 strict 檢查會輸出缺失章序、錯名檔案，以及 `unverified_files`／`stale_files`；只有全部為空且 `complete: true` 才可開始彙總。

### 2.2 錯誤排查與修復
1. **錯名檔案**：若有未依 `ch-<sequence>-extract.md` 命名之檔案，必須手動更名或重新生成。
2. **缺章重補**：針對 Missing 清單列出之章序，單獨調用提取流程補齊缺漏。
3. **續跑起點確認**：確認連續無缺之最新 sequence，將後續章節作為下一輪提取之輸入。

## 3. 全域彙總元數據規範

在完成指定範圍分析並通過 `coverage` 檢驗後，方可撰寫全域彙總文件（如情節單元劃分、爽點排序）。
所有彙總文件之開頭，**必須強制包含本輪起訖章序與跳過章序之元數據標頭**：

```markdown
# 全域情節與改編候選彙總報告

> **本輪分析元數據**
> - 分析模式：指定範圍分析（或全量分析 / 抽樣快評）
> - 本輪起始章序：第 1 章
> - 本輪結束章序：第 50 章
> - 實際分析章數：49 章
> - 索引跳過章序：第 4 章（原因：原著文本缺第 4 章標題）
> - 特殊警示章序：第 5 章（重章與短章警示）
```

嚴禁產出未註明覆蓋範圍之「概括性」或「模糊全書」彙總文件。

## 4. 獨立 QA 狀態管制與檢核表

為維持專業交付標準，分析成果必須進行客觀品質檢核。檢核機制具備獨立性，嚴禁由分析員或自動化腳本自行宣稱通過。

### 4.1 QA 狀態定義
- **待審 (Pending)**：
  - 預設狀態。只要尚未由獨立審核者完成證據抽查與核實，一律標記為「待審」。
  - 嚴禁在無獨立檢核紀錄之情況下標註為通過。
- **通過 (Approved)**：
  - 獨立審核者抽查行號引證無誤、無整段抄錄、無推測腦補、無越權建立正式設定大綱，方可核簽通過。
- **退回 (Rejected)**：
  - 發現行號虛構（幻覺）、引文超過限制、缺漏未明確標籤、或未經授權代替下游做定案決策，予以退回重做。

### 4.2 獨立 QA 檢核表範本
```markdown
# 獨立品質審核檢核表 (Independent QA Checklist)

- 檢核對象目錄：`analysis_output/`
- 檢核章節範圍：第 1 章 至 第 50 章
- 審核日期：202X-XX-XX
- 獨立審核人 / 機制：[獨立審核角色或創作者]
- 當前判定狀態：【 待審 / 通過 / 退回 】

### 檢核指標清單

| 檢核項目 | 標準要求 | 檢核結果 | 審查筆記 / 發現缺陷 |
| :--- | :--- | :---: | :--- |
| **1. 原文唯讀性** | `輸入/` 原文未被修改，無寫入痕跡 | [合格 / 不合格] | - |
| **2. 索引有效性** | 執行 `verify` 命令驗證回傳代碼為 0，且索引含本批來源 SHA-256 | [合格 / 不合格] | - |
| **3. 覆蓋率完整性** | strict `coverage` 回傳 0 缺失章、0 命名錯誤、0 未驗證檔及 0 舊版檔 | [合格 / 不合格] | - |
| **4. 行號引用精確度** | 隨機抽查 5 處引用，起訖行與原文 100% 吻合 | [合格 / 不合格] | 抽查第 3, 12, 25, 38, 45 章 |
| **5. 最短引用遵守度** | 無大段複製原文，僅保留關鍵詞句（<30字） | [合格 / 不合格] | - |
| **6. 腦補排除度** | 原文未交代處皆標示【原文未明確】並列入未決清單 | [合格 / 不合格] | - |
| **7. 提案性質保持** | 人物、世界觀、分集均列為候選，未越權立案 | [合格 / 不合格] | - |
| **8. 彙總標頭元數據** | 彙總檔標明起訖章序、跳過章序 | [合格 / 不合格] | - |

### 審核結論與反饋
- **審核評語**：[若退回，明確條列需修正之章節檔名與具體缺陷]
- **簽核紀錄**：[審核人簽名與時間戳記]
```

### 4.3 防假稱通過機制
任何交付下游 `screenplay-framework` 之成果包中，若 `當前判定狀態` 留空或缺少具體抽查佐證筆記，下游系統與創作者應自動視為「待審」或拒絕接收，以杜絕自動化產出中之虛假合格宣稱。
